# dingflow 数据修改方案说明

## 当前方案

当前 `dingflow` 组件内部会直接修改传入节点对象的深层数据，例如：

```ts
props.node.branches.push(createBranchLine(...))
props.node.branches.splice(index, 1)
branch.children.unshift(createNextNode(type))
props.node.children.splice(index + 1, 0, createNextNode(type))
```

这种写法在 Vue 中可以运行，因为没有直接替换 `props.node` 本身，而是在修改对象内部数组。
**但从设计上看，这属于子组件深层修改 props，不符合严格的单向数据流原则**。

> 这违反了单向数据流原则，子组件不应该直接修改父组件传入的数据。

## 潜在问题

深层修改 props 的主要风险是数据变更来源不够集中：

- 父组件无法清晰知道哪个子组件修改了流程数据。
- 后续实现撤销、重做、变更日志、保存脏状态会比较困难。
- 如果未来接入状态管理、不可变数据结构或后端增量同步，这种写法会成为隐患。
- 递归节点越多，分支、循环内部的数据修改路径越难追踪。

## 为什么暂时保留

当前 `dingflow` 仍处于编辑器原型/功能验证阶段，直接修改深层数据有几个现实优点：

- 实现简单，递归组件之间传参少。
- Vue 响应式可以正常追踪数组变更，界面能及时更新。
- 当前还没有撤销重做、变更审计、复杂保存流程等需求。

因此暂时保留当前方案，避免在基础交互还在调整时引入较多结构性改动。

## 后续推荐方案：事件驱动修改

后续如果要继续发展成真实审批流编辑器，建议改成事件驱动的数据修改方式。

核心原则：

> 子组件只描述“用户想做什么”，不直接修改流程数据；真正的数据修改统一放在根组件或状态层。

可以引入 `path` 表示当前序列在流程树中的位置：

```ts
type FlowPath =
  | []
  | Array<
      | { type: 'branch'; nodeIndex: number; branchIndex: number }
      | { type: 'loop'; nodeIndex: number }
    >
```

事件可以设计为：

```ts
emit('addAfter', path, index, nodeType)
emit('removeNode', path, index)
emit('addBranch', path)
emit('removeBranch', path, branchIndex)
```

根组件根据 `path` 找到对应的 `FlowNode[]` 或 `BranchFlowNode`，再集中执行 `splice/push` 等 mutation。

## 预期改动范围

如果完整重构，主要涉及：

- `types.ts`：新增 `FlowPath` 类型。
- `index.vue`：新增 `resolveNodeList` / `resolveBranchNode`，集中处理所有数据修改。
- `FlowSequence.vue`：接收并透传 `path`，所有修改事件都带上路径。
- `BranchGroup.vue`：不再直接修改 `branches` 或 `children`，改为上抛事件。
- `LoopGroup.vue`：不再直接修改 `children`，改为上抛事件。

组件结构不需要推翻，主要是把“数据修改权”从递归子组件迁回根组件。

## 何时重构

建议在以下功能开始前执行这次重构：

- 撤销/重做
- 节点复制、粘贴、拖拽排序
- 流程保存前校验
- 节点变更记录
- 后端增量同步
- 多人协作或复杂状态管理

在这些能力出现之前，当前方案可以继续保留。

## 折中方案：provide/inject 轻量 Store

除了完整事件驱动方案，也可以考虑使用 `provide/inject` 把流程状态和修改方法下发给递归组件。

这个方案的核心不是把 `props.node` 继续向下传再深层修改，而是把流程编辑器的状态显式抽成一个上下文：

```ts
const flowNodes = ref<FlowNode[]>(createInitialFlow())

function addBranch(branchNode: BranchFlowNode) {
  branchNode.branches.push(createBranchLine(branchNode.branches.length + 1))
}

function removeBranch(branchNode: BranchFlowNode, index: number) {
  branchNode.branches.splice(index, 1)
}

provide(DINGFLOW_CONTEXT_KEY, {
  flowNodes,
  addBranch,
  removeBranch,
})
```

子组件通过 `inject` 拿到上下文后调用方法：

```ts
const dingflow = inject(DINGFLOW_CONTEXT_KEY)!

dingflow.addBranch(props.node)
dingflow.removeBranch(props.node, branchIndex)
```

相比直接深层修改 props，这种方式更明确：子组件修改的是一个被显式共享出来的编辑器状态，而不是父组件通过 props 传入的数据。

### 注意事项

不建议只 provide 一个裸的 `ref`，然后让任意组件自由执行：

```ts
flowNodes.value.splice(...)
```

更推荐 provide “状态 + 修改方法”：

```ts
provide(DINGFLOW_CONTEXT_KEY, {
  flowNodes,
  addAfter,
  removeNode,
  addBranch,
  removeBranch,
})
```

这样可以保留递归组件开发的便利，同时把 mutation 收敛到一组 API 中。后续如果要加入撤销、重做、日志、校验，也可以先从这些方法里扩展。

### 与事件驱动方案的取舍

`provide/inject` 轻量 Store 的优点：

- 不需要层层透传事件，递归组件会更轻。
- 组件可以直接调用上下文方法，代码比完整事件驱动少。
- 比深层修改 props 更符合“显式共享状态”的语义。

它的不足：

- 数据修改仍然可能分散在多个上下文方法里。
- 如果组件绕过方法直接修改 `flowNodes`，仍然会失去变更治理能力。
- 对撤销/重做、协作编辑这类强一致需求，不如完整事件驱动或正式状态管理清晰。

因此可以把它作为中间方案：当前阶段如果想消除“修改 props”的语义问题，但又不想立刻引入 `path + emit` 的完整重构，可以先采用 `provide/inject` 上下文。
